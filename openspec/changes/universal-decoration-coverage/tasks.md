## 3. The sidecar parser + JSON-Pointer resolver

- [x] 3.1 Add `parseFileIntentSidecar(sidecarSource, targetSource)` to `@dusk/core-decoration`: parse the sidecar JSON; parse the target with **`jsonc-parser`** (board R1 — Microsoft/VS Code's; zero runtime deps; native JSONC; NOT `JSON.parse`/`yaml` — `yaml` silently mis-parses JSONC, `JSON.parse` discards positions). Use `parseTree(target, errors, { allowTrailingComma: true })` + `findNodeAtLocation` for RFC-6901 nav; build a one-time `lineStarts` index to convert node `offset`→line (`startLine = lineOf(node.offset)`, `endLine = lineOf(node.offset+node.length-1)`); root pointer `""` → the top node's whole-document span; `findNodeAtLocation` → `undefined` ⇒ hard `unresolved_anchor`; surface `parseTree` `errors[]` ⇒ `malformed_sidecar`; classify comment/string/structural lines for the D4 trivial predicate via `createScanner` (the native tokenizer, not a regex). Resolve each claim/ignore `anchor` to a `[startLine, endLine]` span; emit `DecorationRecord[]` with `verify: "structural"`, `anchor` set, `line` = the **derived** span start, and **`scope`: `"region"` for a non-root pointer / `"file"` for the root pointer `""`** (board region-wiring NIT — the `region` member is exercised by a real path, not dead). A pointer that does not resolve → a structured `unresolved_anchor` error (never a silent skip). Acceptance: `comment-less-decoration` scenarios "A pointer resolves to a current line span after the file is reformatted" + "A dangling pointer is a hard finding". Test plan: colocated tests — resolve a pointer; reformat the target (reorder keys, change indentation) and re-resolve, then **assert the span maps to the claimed key's ACTUAL new line** (board S8 — not merely that the number changed; a bug resolving everything to line 1 must fail this test); delete/rename the key → `unresolved_anchor`.

## 7. Verifier — structural skip

- [x] 7.1 Exclude `verify: "structural"` records from the semantic path **at the index boundary, not just the prompt** (board M1) — across **all four** semantic consumers in `packages/core/index/src/derivedIndex.ts` + `packages/runtime/verifier/`: `focalSupport`, `aspectRollup`, `isSatisfied`, AND **`packages/runtime/verifier/src/antecedent.ts`** (the `compose: implies` antecedent gate — round-2 M1-extension; it reads raw `records` with its own `FOCAL_MARKERS` + `scope:"file"`/`"directory"` predicates, so a structural `intent-file`/`scope:"file"` claim could make a semantic antecedent hold/invert; switch **both** `predicateHolds` and `resolveUnit` to the semantic-only set — it's a module-wide swap, not just the one function). Cleanest: `buildDerivedIndex` exposes a **semantic-only** record set that those four consume; **the public `DerivedIndex.records` field stays the FULL merged set** (round-2 records-contract — structural records MUST remain visible to the reverse-index, `dusk_inspect` claims, and doctor coverage, or the keystone is undone). `doctorStaticAnalysis.ts`'s `S ⊆ D` reads raw `records` intentionally and is benign (config lacks the declaration/body-line shape it matches on). Their "satisfaction" is the mechanical coverage pass (gate green / doctor clean / Stage-2), surfaced via the gate + doctor reports — **not** a separate per-record verdict object (board M3 — do not build one). Acceptance: `verifier-procedure` scenarios. Test plan: (a) a structural record never enters the assembled semantic prompt; (b) a structural `intent-file` claim does NOT flip that intent's aspect to satisfied in `aspectRollup`/`isSatisfied`; (c) **a structural `intent-file`/`scope:"file"` claim does NOT satisfy a `compose: implies` antecedent** (`antecedent.ts` non-contamination); (d) **after the partition, a structural record is STILL visible through `reverse(file)` and the `dusk_inspect` claims list** (keystone preserved — the mirror assertion).
