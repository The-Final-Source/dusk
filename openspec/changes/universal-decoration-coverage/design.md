## Context

v9's total-decoration claim (RFC §4.1, §4.5) is realized only by inline `// @intent` comments, which comment-less formats (strict JSON: `package.json`) cannot carry — so total decoration is not total, and the greenfield POC cannot link its config to intents. A decoration board (3 rounds) designed the closure (RFC App. D.28, Ch. 4.5.4). This change implements it as a standalone v1.x capability and a prerequisite for the POC. Every decision below is the board's converged position; this document pins the seams.

## Goals / Non-Goals

**Goals:**
- Every file not on the ignore set is fully linked to intents — inline (comment-bearing) or via a per-file sidecar (comment-less) — with **computable, enforced line coverage**.
- One decoration model (`DecorationRecord[]`), drift-proof anchoring, mechanical verification for config, a single ignore SSoT.

**Non-Goals:**
- No general any-format region map (JSON-only sidecars; whole-file fallback otherwise).
- No source-map/VLQ machinery, no stored line numbers, no content-hash re-anchoring.
- No change to inline decoration for comment-bearing code (D.11 stands: inline mandatory where possible; sidecars forbidden on commentable files).

## Decisions

### D1 — One model, three parsers; fix the keystone first
Inline (`parseDecorations`), the directory `.intent` (`parseDotIntent`), and the new per-file sidecar all normalize to `DecorationRecord[]` → one `buildDerivedIndex`. It is not a second system. **Keystone:** today the directory `.intent` is parsed *only* by the gate (`packages/delivery/pre-tool-use/src/checks.ts`); the three index walkers (`packages/delivery/mcp-server/src/context.ts` `scanDecorations`, `packages/cli/src/project.ts` `scanDecorations`, `packages/cli/src/doctorStaticAnalysis.ts` `collectSources`) are `.ts`-only and never read it, so `.intent` records never reach the index/Verifier/doctor. Collapse the three walkers into **one shared scanner** in `@dusk/core-decoration` that dispatches by file class and emits the merged `DecorationRecord[]`. Land this FIRST with a test that fails today (a `.intent` record must appear in `buildDerivedIndex` output). *Alternative considered:* add the sidecar parser only to the gate — rejected; it reproduces the exact invisibility bug one layer deeper.

### D2 — Per-file sidecar `<filename.ext>.intent`; basename dispatch; reuse the gated extension
`package.json.intent` sits beside `package.json`. Reusing the `.intent` extension means `isGatedFile` (`packages/delivery/pre-tool-use/src/rejections.ts`) already returns true → auto-gated on the live hook AND the headless `gateWorktreeEdits`, zero `isGatedFile` change. Dispatch by basename: `=== ".intent"` → directory-scope parser (unchanged); ends `.intent` with a non-empty stem → per-file sidecar whose `target` is the stem. *Alternatives:* `<file>.intent.json` (rejected — ends `.json` → silently un-gated, the keystone bug class) and extending the directory `.intent` to address siblings (rejected — a shared file the memory-less Engineer must read-modify-merge each cycle risks clobbering peer claims; per-file is a clean overwrite it owns).

### D3 — Structural anchor stored; line view derived (the drift-killer)
The sidecar stores a **JSON Pointer** (RFC 6901) per claim (`/scripts/build`; `""` = whole document) — the source of truth. **Line ranges are never stored.** They are resolved every run by a location-aware JSON parser (pointer → AST node → `[startLine, endLine]`). The anti-drift property is a **trade, not strict dominance** (honest framing): a pointer is *immune to positional drift* (reformatting, key reordering, whitespace) where the inline line model is not — traded for *sensitivity to key drift* (rename `scripts.build` → `scripts.compile` and the pointer dangles, exactly as a renamed symbol breaks an inline reference). Crucially the key-drift case is **surfaced as a hard `unresolved_anchor` finding, never a silent skip** — so the trade lands on the safe side, and this is why a sidecar is acceptable here though D.11 rejects it for comment-bearing code (where inline is possible). *Rejected:* storing line ranges + content hash ("mimic source-map shapes") — re-imports the positional drift D.11 killed; a source map exists to recover positions after a lossy transform, which does not apply (the target is on disk, re-parseable).

### D4 — Universal full-coverage, computed and hard-blocked
Every file not glob-ignored must be fully covered. Per run: parse the target → resolve every claim/ignore anchor to a span → `covered = ⋃ intent-spans`, `ignored = ⋃ ignore-spans`, `uncovered = non-trivial-lines − covered − ignored`. **Any `uncovered ≠ ∅` hard-blocks** (full coverage ALWAYS — the operator's directive); the finding reports the **target's** `file:line`, not the sidecar's. Whole-file (`@intent-file` / root pointer `""`) is the maximal tile and the only honest unit for unstructured targets (containment survives as the floor). **It is also the default (R2):** emit a single whole-file claim unless the file genuinely serves multiple distinct intents, in which case — and only then — tile it with per-key `scope:"region"` claims. A whole-file claim on a multi-intent file is a *false attribution*, so the per-key trigger is an honesty rule, not an ergonomic one.

**"Non-trivial" is defined explicitly for JSON/JSONC, not by analogy.** The gate's existing `CLOSING_ONLY_RE`/`isBlank` were written for *TypeScript* punctuation and MUST NOT be reused verbatim — in real JSON the load-bearing content sits on lines like `"build": "tsc",`, which are neither blank nor bare-bracket. The predicate is evaluated **after the location-aware tokenizer classifies each line** (comment vs string vs structural) — NOT as a raw regex over physical lines — so a multi-line string value whose continuation contains `{`/`}`, or a value sharing a line with a `/* …` block-comment open, is attributed by token, never mis-scored by naive line shape. On that tokenized view, a line is **trivial** iff it is (a) empty, OR (b) solely structural tokens (`{`, `}`, `[`, `]`, `,`, `:`) and whitespace (opens/closes a container or separates, carrying no key or scalar), OR (c) — since JSONC is in scope (D9) — a **comment line** (`//…`, a `/* … */` line, or a `*`-led continuation): a comment carries no authored config value and cannot be JSON-Pointer-anchored, so requiring its coverage would make any commented JSONC target permanently un-coverable. A line bearing a key (`"scripts": {`) or a scalar value is **non-trivial** and must be covered. This predicate is pinned by a unit test that enumerates the exact non-trivial line set for both a real `package.json` and a JSONC fixture with comments (see tasks §5.3) — coverage is computed against a specified predicate, never a TS-regex's "spirit."

### D5 — `decoration.ignore` glob SSoT; two-tier ignore
`dusk.config.yml` gains `decoration.ignore: [<globs>]` with built-in defaults merged with project additions — the **single** set consumed by the gate, the coverage scanner, and doctor. The defaults span three categories (named so the silent exemptions are honest, not buried in a flat list): **dependencies** (`node_modules/**`, `.git/**`), **generated/build output** (`.ia/runtime/**`, `dist/**`, `build/**`, `coverage/**`, `**/*.lock`), and **secrets** (`.env*`). The default ignore set IS the honest boundary of "total" coverage — what it lists is what "every file" does *not* mean.

**It replaces ALL THREE hardcoded skip sets, not one.** The board verified three divergent hardcoded skip sets exist today: `packages/delivery/mcp-server/src/context.ts` (`SKIP_DIRS`), `packages/cli/src/project.ts` (`SKIP_DIRS`), and `packages/cli/src/doctorStaticAnalysis.ts` (`SKIP_DIRS`) — with different members (`.turbo`/`.next` in two, `.claude` in one). When the three walkers collapse into the one shared scanner (D1), **all three skip sets are subsumed** into `decoration.ignore`. Replacing only `doctorStaticAnalysis.ts`'s set would leave two shadow copies and re-fragment the very SSoT this establishes.

Two tiers, never conflated: (1) the **glob ignore** exempts whole files/dirs that are out of scope; (2) the per-claim **`@intent-ignore`** marker exempts a documented region *within* a covered file (with because/reason). Glob-ignored files are not gated, not coverage-checked, not flagged. **The generated-file boundary follows a principle, not a per-file verdict:** an artifact that is *checked into source and meaningfully authored against intents* (e.g. `package.json`, configs, migrations) is **covered** (via sidecar); *pure machine build output* (`dist/`, lockfiles) is **ignored**. Migrations are covered (a human/agent authored their intent); lockfiles are ignored (no authored intent) — the same principle decides both, rather than each being enumerated by fiat.

### D6 — Config verified mechanically/structurally; never the semantic *path* (not just the prompt)
A manifest carries no architectural triple to judge. Sidecar/comment-less records are tagged `verify: "structural"` so they are excluded from the **semantic path at the index boundary** — NOT merely from the assembled prompt. This is the load-bearing correction: the keystone (D1) deliberately routes structural records into `buildDerivedIndex`, and the satisfaction-bearing functions key on `marker`/`scope` alone and are blind to `verify`. The exclusion SHALL cover **all four** semantic consumers:
- `focalSupport` — a sidecar's `intent`/`intent-file` marker is in `FOCAL_MARKERS`, so the record would surface as focal evidence;
- `aspectRollup` — an `intent`/`intent-file` record marks that intent's aspects **claimed/satisfied**;
- `isSatisfied` — recurses on the rollup;
- **`packages/runtime/verifier/src/antecedent.ts`** (the `compose: implies` antecedent gate — the fourth consumer, easy to miss): it reads `index.records` **raw** with its own `FOCAL_MARKERS` + `scope:"file"`/`"directory"` predicates, so a structural `intent-file`/`scope:"file"` claim could make a semantic antecedent **hold** (`"is enclosed by a decoration of"`, `"claims any aspect of"`, `"is decorated with"`) — or invert it under `polarity: negative`. A semantic antecedent decided by a config claim is the same "blended into semantic adherence" violation.

**The public `DerivedIndex.records` field SHALL remain the FULL merged set** (structural records visible) — the keystone's entire purpose is to make `.intent`/sidecar records visible to the reverse-index, `dusk_inspect` claims, and the doctor coverage report, and narrowing `records` to semantic-only would silently re-hide them and undo the keystone. The semantic/structural split is therefore an **internal partition** consumed only by the four satisfaction-bearing functions above (cleanest: `buildDerivedIndex` exposes a semantic-only record set those four consume, alongside the full `records`). The acceptance tests assert both directions: (a) a structural `intent-file` claim does **not** flip a semantic aspect to satisfied nor satisfy a `compose: implies` antecedent (non-contamination); (b) a structural record **remains visible** through `reverse(file)` and the `dusk_inspect` claims list after the partition (keystone preserved). **The four above are the complete set of consumers that can flip a semantic verdict/satisfaction/antecedent** — the consumer census is exhaustive, and the remaining raw-`records` readers are benign **by data shape** (documented so the census is provable, not lucky): `doctorStaticAnalysis.ts`'s `S ⊆ D` pass — config records lack the declaration/body-line shape its `unitIntents` matching requires (stays TS-scoped); `testDiscovery`/`testChildrenByLayer` — filter on test markers (`intent-test`/`intent-test-file`), which a structural config record never carries (D8: sidecars emit only `intent`/`intent-file`); and the registry `getAdherenceSummary`'s `claimed_in_package` — deliberately full-set **presence** (consistent with reverse-index visibility), not satisfaction, so it cannot flip a verdict. `reverse`/`forward`/inspect/stats/snapshot are non-semantic and correctly keep the full set.

**Mechanical "satisfaction" is the coverage pass, not a per-record verdict object.** There is no parallel mechanical *verdict* engine in v1.x: a structural record is "satisfied" exactly when its anchor resolves and the target's coverage holds (gate green / `dusk doctor` clean) and Stage-2 build/test passes. That is reported on the mechanical channel **via the gate result and the doctor coverage report** — the spec does not promise a separate per-record satisfaction object, and §7 does not build one. (Avoids over-claiming a reporting channel that isn't constructed.)

**Accepted limitation (recorded, not silent):** structural verification confirms *presence + anchoring* (every line is claimed by an intent that exists), NOT the *correctness of the binding* — a sidecar can claim `/scripts/build` serves a structurally-valid `intent_path` that is semantically wrong, and nothing judges that mapping (config has no NL triple to discourse over). This is an accepted trade-off of keeping config off the semantic channel, not an oversight.

### D7 — Enforcement split: per-write structural validity; post-hoc pair-state coverage
The two files (target + sidecar) may be written in separate tool calls, so the **per-write live hook** runs only single-file structural validity (sidecar parses; intent paths/aspects/ignore vocab resolve) — it does NOT run cross-file tiling (the other file's post-edit content isn't reliably co-present). The **full coverage tiling runs in the post-hoc `gateWorktreeEdits`** (`packages/cli/src/implement.ts`) over the settled worktree, where both files are present and write-order is irrelevant. Doctor re-runs coverage off the write path. This avoids false-blocking legitimate two-step edits while still guaranteeing coverage on the converged state.

**Implementation note — this is a restructure of `gateWorktreeEdits`, not an additive hook.** Today `gateWorktreeEdits` is a **per-file loop** calling `runGate` once per changed file; `runGate` is single-file and cannot express cross-file coverage (a target's coverage depends on its sidecar, a different file). The function becomes a **two-phase whole-worktree pass**: phase 1, per-file structural validity via `runGate` (as today); phase 2, a worktree-level coverage tiling step that pairs each non-ignored target with its sidecar and computes `uncovered`. The implementer must not try to bolt tiling into the existing per-file `runGate` call.

### D8 — `DecorationRecord` schema delta (additive)
Add `anchor: string | null` (the JSON Pointer; `null` for inline/directory records), a `region` scope member, and a `verify: "structural" | "semantic"` discriminator (default `semantic`, sidecar records `structural`). All additive with defaults so every existing record + parser is unchanged. The sidecar parser emits records whose `line` is the derived span start and whose `anchor` carries the pointer. **The `region` member is wired, not speculative:** a per-key sidecar claim (a non-root JSON Pointer) emits `scope: "region"`; the whole-file claim (root pointer `""`, marker `intent-file`) emits `scope: "file"`. This keeps `region` exercised by a real path (and tested) — no dead enum member — and means a structural whole-file claim is `scope:"file"` (the exact shape `antecedent.ts` inspects, which is why D6 must partition it off the antecedent gate).

### D9 — Scope JSON-only; refuse the over-engineering traps
JSON (and JSONC) sidecars only; any other comment-less format gets whole-file `@intent-file` coverage until a real second structured format demands more. Explicitly refused (board-named): a general any-format region map / per-format parser registry; source-map/VLQ machinery; content-hash re-anchoring; a schema-migration framework (one literal `schema_version: 1`).

## Risks / Trade-offs

- **[Keystone regression]** Adding the sidecar parser to only the gate reproduces the invisibility bug → land the shared scanner first, with a test that fails today and asserts a sidecar record reaches `buildDerivedIndex`.
- **[Location-aware JSON parser becomes a per-format zoo]** → ship JSON/JSONC only; whole-file fallback for everything else.
- **[Two-file write ordering false-blocks]** → coverage tiling only in the post-hoc pair-state gate, not per-write (D7).
- **[Coverage flooding on deps/generated files]** → the `decoration.ignore` SSoT with conservative defaults; whole-file `@intent-file` is a one-line cover for the rest.
- **[Dangling pointer treated softly]** → it MUST be a hard finding; soft-handling reopens the drift hole that justified storing structural anchors.

## Migration Plan

Additive within the dusk monorepo. Sequence: (1) keystone shared scanner + failing test; (2) `DecorationRecord` schema delta; (3) sidecar parser + JSON-Pointer resolver; (4) `decoration.ignore` config + SSoT plumbing (replace `SKIP_DIRS`); (5) gate coverage checks + rejection kinds (per-write validity + post-hoc tiling); (6) doctor coverage report; (7) Verifier structural-skip. Existing inline decoration and the directory `.intent` are unchanged in behavior (the keystone only makes the latter *visible*). Then the greenfield POC restarts from scratch with full coverage available.

## Resolved decisions (were Open Questions — settled by arch board)

### R1 — Location-aware parser: **`jsonc-parser`** (Microsoft/VS Code's). *(was Q1)*
Decided unanimously. The board first checked reuse: the repo's incumbent structured parser is `yaml@2.8.2`, but an **empirical test disqualified it** — `yaml` parses a JSONC fixture (with `//` comments) **silently wrong** (zero errors, the pointer target vanishes), the worst failure mode for a coverage-load-bearing parser and a direct "no silent behavior" violation. No location-aware JSONC parser exists in the lockfile, so this is a genuine new dependency; `jsonc-parser` is the right one:
- Native JSONC (comments + trailing commas via `{ allowTrailingComma: true }`); `parseTree` + `findNodeAtLocation` is literal RFC-6901 navigation; per-node `offset`/`length`; **zero runtime deps**; the parser inside VS Code's JSON tooling. Runner-up `@humanwhocodes/momoa` (native `loc` but no built-in pointer nav — you'd re-implement `findNodeAtLocation`); `json-source-map` eliminated (strict JSON, no comments → fails D9).
- **Implementation notes (for tasks §3.1):** (a) `jsonc-parser` returns char offsets, not lines — build a one-time `lineStarts` index and binary-search offset→line (`startLine = lineOf(node.offset)`, `endLine = lineOf(node.offset+node.length-1)`); (b) `findNodeAtLocation` returns the **value** node (good — that's the `region` span; D4 scores by line so the key on the same line is still attributed); (c) root pointer `""` → the `parseTree` top node's `[offset, offset+length]` = whole document; (d) `findNodeAtLocation` → `undefined` maps directly to the hard `unresolved_anchor` finding; (e) also surface `parseTree`'s `errors[]` → `malformed_sidecar` (this is the explicit-error behavior `yaml` lacked); (f) use the `createScanner` token stream to classify comment/string/structural lines for D4's trivial predicate — the native tokenizer, not a regex.
- Honors all 5 architecture MUSTs: pointer→node→span never reversed (no stored line data); `""` whole-doc; comment-preserving tokenizer; token-level (not physical-line) attribution; dangling = hard finding.

### R2 — `@intent-file` default: **whole-file by default; per-key regions ONLY when a file genuinely serves multiple distinct intents — an honesty requirement, not ergonomics.** *(was Q2)*
Decided unanimously; the operator's whole-file instinct confirmed and sharpened. **Default:** one whole-file claim (`anchor: ""`, marker `intent-file`, → `scope:"file"`). **Deviate to per-key `scope:"region"` claims iff** the file's non-trivial lines are authored against **two or more distinct intents** and the index should record which region serves which. Rationale:
- **Per-key feeds no AI reasoning consumer.** `reverse(file)`/`forward(intent)` key on `file`/`intent_path` and dedupe through a `Set` (`derivedIndex.ts`) — per-key anchors are invisible to the reverse-index (they collapse in the Set). And structural records are partitioned out of all four semantic consumers (D6). So finer granularity is *purely mechanical bookkeeping*, never an input to reasoning — and v9's "ergonomics are for AI consumers only" reframe therefore argues *against* per-key-by-default, not for it.
- **Coverage is satisfied by the floor.** A root `""` claim's span is the whole document → `uncovered = ∅` by construction (D4). Per-key is always additive information, never a coverage necessity, so it cannot be the default on coverage grounds.
- **The inline analogy does NOT transfer.** Inline decoration is per-statement because each unit carries an architectural triple the *semantic* channel judges; config has no triple (D6, structural-only). Mirroring inline's granularity for config is cargo-culting the form without the function.
- **But flat "whole-file always" is dishonest on a multi-intent file.** A single whole-file claim on a `package.json` whose `scripts` serve a build intent and `dependencies` serve runtime intents is a *false attribution* — the blended-metric sin. So the trigger for per-key is **factual and decidable** ("does this one file serve >1 distinct intent?"), framed as honesty, not taste. The mechanism already exists (D8 wired `region`; D2 sidecars are clean overwrites), so deferring per-key to where it's honestly needed carries zero lock-in.
