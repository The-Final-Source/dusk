## Why

Phase 1 shipped the substrate (schema, parser, decoration, index, gate, init/doctor) but contains **no model and no Verifier**. Without Phase 2, the system can parse and gate decorated code but cannot *judge* it — none of the Verifier's load-bearing v9 properties (runtime polarity inversion, deterministic `compose: implies` antecedents, the `focal_verdict` + `support_quality` split, scoped per-aspect reading) exist yet, and no sub-agent role can spawn. Phase 2 is also the first phase where a model enters the loop, so it is the only place where these properties become **falsifiable** against the real LLM. Pipeline (Phase 3), Authoring (Phase 4), and Validation (Phase 5) all bind to Phase-2-defined interfaces — the Verifier procedure, the spawn pipeline, the memory model, and the read-path MCP surface — so Phase 3 cannot start until this phase lands cohesively.

This change delivers **exactly Phase 2 of the v9 implementation plan** (`docs/rfcs/001-mvp-rfc/v9-implementation-plan.md` lines 211–380), grounded in RFC §3.1–§3.3, §3.2.1, §9.1, §9.2, §9.4–§9.7, §9.9, §10.1, App. A.4, App. A.6, App. A.9, App. A.11, App. D.17, App. D.18, and App. B.

## What Changes

- **9 sub-agent role files** under `.claude/agents/dusk-*.md` with v9 frontmatter (`dusk_role_version: 2`, `memory`, advisory `tools`, `skills`, `model`) and complete role-body content per RFC §9.5. The **`dusk-verifier.md` prompt template ships complete** — two-path execution structure for `compose: implies` ("antecedents already evaluated deterministically; you receive only consequents"), explicit affirmative-framing contract (no "invert if negated" branch), and 2 positive + 2 negative few-shots drawn from App. B.
- **Tier-1 skills shipped complete** (`dusk/verifier/triple-evaluation`, `code-span-scoping`, `polarity-aware-evaluation`, `implies-evaluation`; `dusk/engineer/decoration-completeness`, `statement-extraction`; `dusk/author/polarity-decision`, `implies-antecedent-grammar`); Tier-2 skills at baseline.
- **`packages/runtime/orchestrator/spawn`** — `spawnSubAgent({role, beadId?, dialogId?, sessionId, input})` that materializes memory + injects skills **before** the Claude Code Task call (`subagent_type: dusk-<role>`), emits a `SubAgentTrace` with `skills_loaded[]` and `iteration_number?` per App. A.6, and — in **test/benchmark mode only** — records the verbatim assembled system prompt as `raw_prompt` (NEW per board round 4; the observable surface that P2-T1/T3/T5/T17 assert against, replacing the lossy `input_summary`). `dusk_role_version` range is enforced (P2-T19).
- **`packages/runtime/memory`** — materialization for all four scopes (`none` / `bead` / `dialog` / `session`); the **structured dual-channel bead-memory format** (impl + test-authoring channels per §9.6.1); **mechanical-only compaction** (never LLM-summarized) that bounds memory size across iteration depth; and the **load-bearing diagnosis-routing guarantee**: the Engineer's convergence diagnosis informs the Bead Orchestrator only and is structurally absent from every Verifier spawn payload.
- **`packages/runtime/skills`** + **`packages/runtime/tool-scope`** — advisory skill injection + advisory tool scoping per §9.4 / §9.7; the gate (Phase 1) remains the real safety boundary.
- **`packages/runtime/verifier`** — the full §3.3 procedure: focal+support claimant resolution → scoped evidence reading → **deterministic index-lookup antecedent evaluation for `compose: implies`** (closed predicate vocabulary; emits *zero* Verifier Task calls when the antecedent is false) → affirmative prompt build with `quantifier` bound + `scope` → LLM verdict at `temperature: 0` → **runtime polarity inversion** outside the LLM call → per-support `triple_verdict ∈ {matches, mismatch, vague}` → `support_quality` aggregation → per-`compose` aggregate. Output shape per App. A.4 (`implies_antecedent_held?`, `focal_verdict` + `support_quality`, `support_pass_count`, `polarity`). Ambiguous antecedents return a structural `DuskError` — never an LLM fallback.
- **`packages/runtime/verifier-test-double`** — **scripted-verdict Verifier double** (Phase 1's deferred design D7). Pluggable into `spawnSubAgent` via a test flag; returns scripted verdicts from a fixture without any model call; records spawn-counter telemetry. The substrate that every Phase-3 control-flow test (budgets, stuckness, confirmation, livelock, recovery ladder, cancel) will bind to.
- **`packages/delivery/mcp-server`** — MCP scaffolding + **`dusk_status`, `dusk_inspect`, `dusk_verify`** + paired read-only fallback tools **`dusk_list_intents` / `dusk_get_intent` / `dusk_list_traces` / `dusk_list_beads` / `dusk_get_bead` / `dusk_list_implement_checkpoints`** + read-only MCP **resources** mirroring the tools. **`DuskError` envelope on every tool** (App. A.11). Every fallback tool is structurally equivalent to its paired resource.
- **`packages/cli` extensions** — `dusk verify` / `dusk inspect` mirrors + `dusk roles` / `dusk skills` introspection commands.

## Capabilities

### New Capabilities

- `sub-agent-runtime`: Spawn-by-role-name via the Claude Code Task tool, with Dusk-side materialization (memory + skills + role body + raw_prompt capture in test mode) before the spawn call, advisory tool/skill scoping, role-version refusal, and full `SubAgentTrace` emission per App. A.6.
- `memory-materialization`: Four memory scopes (`none` / `bead` / `dialog` / `session`); dual-channel bead memory; mechanical-only compaction with bounded size across iteration depth; the diagnosis-routing guarantee (diagnosis is structurally invisible to the Verifier).
- `verifier-procedure`: The §3.3 procedure end-to-end at `temperature: 0` — focal+support scoped reading, deterministic-index-lookup antecedent evaluation for `compose: implies`, affirmative prompt construction with runtime polarity inversion, quantifier cardinality + `scope` enforcement, verdict split (`focal_verdict` + `support_quality`), per-claim support `triple_verdict`, `compose` aggregation, and the `support_pass_count` summary.
- `mcp-read-surface`: MCP server + read-only tools (`dusk_status`, `dusk_inspect`, `dusk_verify`), paired list/get fallback tools, equivalent MCP resources, and uniform `DuskError` envelope.
- `verifier-test-double`: Scripted-verdict Verifier double + spawn-counter telemetry — the test substrate Phase-3 control-flow tests bind to.

### Modified Capabilities

- `dusk-cli-substrate`: Add `dusk verify`, `dusk inspect`, `dusk roles`, `dusk skills` commands mirroring the read-path MCP tools; `--help` works on each.

## Impact

- **New packages:** `packages/runtime/{orchestrator/spawn, memory, skills, tool-scope, verifier, verifier-test-double}`, `packages/delivery/mcp-server`. CLI extensions to `packages/cli`.
- **Bound to Phase-1 seams (no changes):** schema types (`Intent`, `Triple`, closed-vocabulary antecedent union, five-kind `RelatesTo`), the decoration record, the derived-index query interface (forward / reverse / focal+support / aspect-rollup / test-discovery + hierarchical satisfaction), `Rejection`/`HookInput`/`HookOutput`, `dusk.config.yml` shape, the test harness (temp-repo factory + injectable `Clock`).
- **App-package surface (api/web/shared/hooks/mobile):** untouched (Phase-5 dogfood targets).
- **External dependency:** Anthropic SDK for real-frontier-model calls in P2-T5..T18 (used at `temperature: 0`; control-flow tests use the Verifier double and remain zero-model).
- **Determinism posture:** single frontier-tier model across roles per `dusk.config.yml > models.default`; `temperature: 0`; control-flow tests are zero-model via the double; verdict-correctness tests are explicit-N statistical with pre-registered thresholds.
- **Non-goals:** Decomposer, worktrees, short cycle, long cycle, Test Runner, recovery ladder, livelock, commit, merge, `dusk_cancel`, pause/resume, Author dialog flow, fresh-Verifier audit, static-analysis doctor, observability sinks, benchmark harness, dogfooding. These are Phase 3/4/5 contracts. `index_snapshot_id` is present-but-optional on traces in Phase 2 (no session snapshot exists until Phase 3).
