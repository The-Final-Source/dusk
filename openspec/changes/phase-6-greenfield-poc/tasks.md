# Tasks — Phase 6: Greenfield POC

> **Two repos.** Tasks under §1, §5, §6, §7 (tooling/schema/feedback) run in the **dusk monorepo**. Tasks under §2, §3, §4 (the application build) run in the **standalone POC repo**, driven by the linked `dusk` CLI from the monorepo. Each task states its repo.
>
> **Determinism.** The audit tooling, transcript checker, and `PocReport` evaluator (§1.2, §5, §6) are **zero-model pure passes** with Vitest unit coverage. The build itself (§3, §4) runs the **production pipeline against the real frontier model** (ambient Claude Code CLI, no API key, `temperature: 0`, the Phase-4 transport-failure amendment applied) — its acceptance is real-run, not a scripted double.

Test plan: colocated `pocReport.test.ts` (unit-only, pure) — parses a canonical fixture of each section; rejects an exploratory metric placed in the gating section (`.strict()`); rejects `gating: true`.

- [x] 1.3 **(dusk repo → throwaway sibling repo)** De-risk Dusk-against-an-external-repo BEFORE the real build (design D3). **Surfaced + fixed the first real D11 defect:** `dusk init`'s `DEFAULT_HOOK_COMMAND` hard-coded `$CLAUDE_PROJECT_DIR/node_modules/@dusk/pre-tool-use/dist/cli.js`, which resolves to a nonexistent path in an external repo (no `@dusk/*` in its node_modules) → gate fails open + `dusk doctor --check-hook` errors. Worktree creation + `node_modules` symlink are proven by the first real `dusk implement` in §4. Against a disposable sibling repo outside the monorepo: prove (1) worktree creation under the external root, (2) the `node_modules` symlink strategy the dogfood-grade `dusk implement` uses, (3) gate resolution (`$CLAUDE_PROJECT_DIR` install + `checkHook` expansion + `gateWorktreeEdits`/worktree paths relative to the external root). Acceptance (`greenfield-poc-build` scenario "The external-repo path is de-risked before the real build"): a trivial gated `dusk implement` lands a trailer-bearing commit in the sibling repo; any path assumption that breaks is fixed as a tightly-scoped dusk-repo change with a regression test + spec delta only if mis-specified (design D11). Test plan: the de-risk run is documented in the change; any D11 fix carries its own colocated regression test in the affected dusk package.

- [x] 1.4 **(dusk repo)** Close the structural-satisfaction gap surfaced by the first all-config intent (design D11; RFC App. D.29; spec delta `verifier-procedure`). The first foundation intent (`project/typescript-esm-foundation`) looped the short cycle and never converged because its triples' only claimants were `verify: "structural"` sidecar records, which D.28 partitions out of the semantic evidence set → the LLM Verifier defaulted them to `fail` forever. Fix: (1) additive optional `channel: "mechanical" | "semantic"` on `PerTripleVerdict` (`packages/core/schema/src/verdict.ts`); (2) `structuralAspects`/`semanticAspects` classifiers on the derived index (`packages/core/index/src/derivedIndex.ts`); (3) zero-LLM `structuralVerdict` + `mergeStructuralSemantic` (`packages/runtime/verifier/src/structural.ts`) reusing the gate's coverage primitives; (4) channel routing in the `verifierFactory` (`packages/cli/src/implement.ts`) — all-structural → structural, all-semantic → unchanged `verifyIntent`, mixed → merge per `triple_id`. The short cycle and semantic path are untouched. Acceptance (`verifier-procedure` scenarios): an all-structural config intent converges iteration 1 with zero model calls; a dangling anchor / uncovered line / unclaimed aspect fails mechanically; a both-ways triple passes only if both channels pass. Test plan: `packages/runtime/verifier/src/structural.test.ts` (6 cases) + `structuralAspects`/`semanticAspects` cases in `derivedIndex.test.ts`; full `pnpm typecheck` green.

- [x] 1.5 **(dusk repo)** Decouple the verification CHANNEL from decoration MODALITY — first-principles completion of 1.4 (design D11; RFC App. D.30; spec delta `verifier-procedure`). Re-running the foundation build proved D.29 incomplete: `verify` was sourced 100% from the parser (inline→semantic, sidecar→structural), so a comment-bearing config file (`vitest.config.ts`) was forced onto the semantic channel and could not converge. Fix: (1) author-declared `verify: "structural" | "semantic"` on `TripleSchema` (`packages/core/schema/src/primitives.ts`), default absent ≡ modality fallback; (2) triple-first channel resolution in `structuralAspects`/`semanticAspects` (`derivedIndex.ts`) — explicit `triple.verify` wins, else modality; (3) inline-backed structural path in `structuralVerdict` (`structural.ts`) — presence, not JSON coverage; (4) Stage-4 drafting rule + `dusk/author/verify-channel` skill so the dialog elicits the channel per triple. Decorator-declared channel was rejected (Engineer-could-downgrade honesty hazard); no new marker. Acceptance (`verifier-procedure` scenarios): a comment-bearing config triple marked structural converges zero-LLM; an author-declared semantic triple is not swept structural by a whole-file claim. Test plan: D.30 cases in `structural.test.ts` (inline-backed pass, no sidecar read) + `derivedIndex.test.ts` (author override both directions); full `pnpm typecheck` green.
