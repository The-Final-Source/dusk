## Why

A Phase-6 POC build surfaced a verified gap (RFC App. D.32): **"is this a test intent?" is decided two inconsistent ways.** The orchestrator's Stage-2 test execution and `dusk_inspect` decide it by the intent's **authored path suffix** (`…/unit-tests` etc., from `test_pyramid.suffixes`); the CLI verifier, the Stage-1 test-body pre-pass, and the test-runner decide it by the **decoration marker** (`@intent-test`/`@intent-test-file`, via `testDiscovery`). When an Engineer decorates a test file with `@intent` instead of a test marker — which it does, because **it was never taught the test markers exist** (`ENGINEER_FILE_INSTRUCTION` and every `dusk/engineer/*` skill name only `intent`/`intent-file`; the per-bead task is a bare `Implement <path>` with no test signal) — `testDiscovery` returns empty and the CLI verifier (`cli/src/implement.ts:354`) **silently falls through** to ordinary verification. A test-pyramid intent's `covers-*` triples are then judged from a single `@intent` line's evidence by the ordinary channel, which has **no notion of test falsifiability** — so a tautological, mock-only, or never-failing "test" can be **silently accepted**, defeating the two-stage test satisfaction guarantee (RFC §3.4) and violating the project's "no silent behavior" rule.

This change resolves the gap from first principles, ratified by a four-member arch board (architect, backend, AI eng, Fowler) over an investigate→debate→converge cycle. The board's resolution applies the **D.30 principle to a new axis**: a routing decision must follow an **authored property of the claim**, not a fallible decoration artifact. Test-identity is an authored fact — the **path suffix** — fixed before any code is written; the **marker** is the Engineer's downstream restatement. So routing follows the suffix; the marker keeps a *different, genuinely load-bearing* job — **locating the test body** the pre-pass must read (which a suffix cannot do). The two were conflated; this change separates them and makes the silent path structurally impossible.

Grounded in RFC App. D.32 (+ the D.29/D.30/D.31 verification-channel series it extends), §3.4 (two-stage test satisfaction), §3.4.1, §4.6 (the PreToolUse gate), App. A.8 (rejection kinds).

## What Changes

- **Routing by authored suffix (the root fix).** The CLI `verifierFactory` (`cli/src/implement.ts:352-356`) routes a test intent to the Stage-1 test-body pre-pass when the intent's **path ends in a configured `test_pyramid.suffixes` value** — NOT when `testDiscovery(path)` is non-empty. A test-suffix intent therefore can **never** fall through to ordinary `verifyIntent`; the silent-accept becomes structurally unreachable rather than guard-dependent. This brings the CLI verifier into line with the orchestrator + `dusk_inspect`, which already route by suffix — collapsing the two-way inconsistency to **one source of truth (the suffix)**.
- **The marker keeps its real job: body location.** `@intent-test`/`@intent-test-file` remain the file→test-intent link the pre-pass / test-runner use to find *which file* is the test body (`testDiscovery`). The marker is **not** dropped and **not** derived from the suffix — it carries information the suffix cannot (which file/region). The split is explicit: **suffix = identity/routing (authored); marker = evidence location (Engineer-supplied, required, enforced).**
- **Fail loud on a missing body, legibly.** When a test-suffix intent routes to the pre-pass but `testDiscovery` is empty (no test-marker claimant), the pre-pass / test-runner SHALL fail with a **specific** signal — `test_intent_no_test_marker` naming the intent and the expected markers — never a silent skip and never the generic "test does not verify its claims." This lets the short cycle self-correct instead of churning to budget.
- **Reverse of gate Check 9 (mechanical enforcement of the marker invariant).** A new gate check: a **focal** claimant (`intent`/`intent-file`) whose `intent_path` *is* a test-suffix intent is rejected (`non_test_marker_on_test_intent`) with a fix-it message pointing at `@intent-test`/`@intent-test-file`. This guarantees the body-locating marker is present at **write time** — the earliest, cheapest, most actionable point — so the pre-pass body is reliably findable without relying solely on probabilistic guidance. **Scoped precisely** (resolves the "is `@intent` ever legitimate on a test file?" question): it fires ONLY on a focal marker claiming *the test-suffix intent itself*; `@intent-support` lines, and `@intent` claiming a *non-test* intent that happens to live in a test file, stay legitimate and untouched.
- **Teach the Engineer (liveness).** `ENGINEER_FILE_INSTRUCTION` + a `dusk/engineer/*` skill SHALL teach that a file implementing a test-suffix intent must claim it with `@intent-test-file <path>` (file scope) or `@intent-test` (declaration scope), never `@intent`; and the per-bead Engineer task SHALL carry an explicit "this is a test bead" signal when the target intent path ends in a configured suffix. Routing-by-suffix makes failure *honest*; this makes success *possible* (the pre-pass needs the marker-located body to ever pass).

## Capabilities

### New Capabilities

- `test-intent-routing`: Test-pyramid intents are routed to the two-stage test pre-pass by their **authored path suffix** (the single source of truth for test-identity); the `@intent-test`/`@intent-test-file` marker locates the test body; a routed test intent with no discoverable body fails loud (`test_intent_no_test_marker`), never silently; the Engineer is taught the test markers and signalled when a bead is a test bead.

### Modified Capabilities

- `pretooluse-gate`: Adds the reverse of Check 9 — a focal claimant of a test-suffix intent must be a test marker (`non_test_marker_on_test_intent`), scoped to the focal claim of the test-suffix intent itself. The forward Check 9 (test-marker ⇒ test-suffix path) is unchanged; together they enforce the invariant *test-suffix intent ⟺ test-marker claimant present*, which makes the suffix-based and marker-based consumers provably agree.

## Impact

- **Code touched (dusk monorepo):** `cli/src/implement.ts` (routing by suffix at `:352-356`; `ENGINEER_FILE_INSTRUCTION` at `:187-200`; per-bead test signal); `delivery/pre-tool-use/src/checks.ts` (reverse Check 9 + new rejection kind in `rejections.ts`); `runtime/benchmark/src/testPrepass.ts` + `runtime/test-runner/src/{run,discovery}.ts` (fail-loud-legible on empty body); `cli/assets/skills/dusk/engineer/*` (a skill teaching test-file decoration). The shared suffix predicate (`testPyramidSuffixes(config)`, already in `core/schema`) is extracted/reused so there is **one** implementation, not three copies (`stateMachine.ts`, `queries.ts`, the new CLI call).
- **Bound, not reshaped:** `derivedIndex.ts` `TEST_MARKERS`/`testDiscovery` (still the body-locator); the structural/semantic partition (D.29/D.30/D.31 — orthogonal: test routing is a *prior* fork choosing the instrument; structural-vs-semantic is *within* the ordinary path); the suffix-based consumers (`stateMachine.ts`, `queries.ts`) are correct as-is and are made *consistent* by the invariant, not rewritten.
- **The two-way inconsistency dissolves:** with the reverse-Check-9 invariant enforced, "ends in suffix" and "has a test marker" always agree, so the blast-radius consumers (`testChildrenByLayer`, Stage-2 execution, inspect rollups) need no separate fix.
- **Determinism posture:** routing-by-suffix, the reverse gate check, and the fail-loud-empty-body guard are **zero-model mechanical** (the correctness guarantees, tested deterministically). The Engineer guidance is the one model-facing piece — it improves first-pass success but is never relied on for correctness (the mechanical guards make the gap unrepresentable).
- **Non-goals:** NOT dropping the marker / deriving it from the suffix (it locates the body — a suffix can't; "derive from suffix" was explicitly rejected by the board). NOT a third `verify`-channel value (test-routing is a separate axis from structural/semantic). NOT a new authoring field (`kind: test`) — the suffix already declares test-identity; adding one would create a third routing axis to keep consistent. NOT touching the POC repo or the Phase-6 change.

## Verifiability / acceptance

Success = the silent-accept is **structurally impossible** and the failure modes are loud and legible:
- A test-suffix intent **always** routes to the Stage-1 pre-pass regardless of its decoration marker; it can never reach ordinary `verifyIntent`. (Unit: a `DerivedIndex` with a test-suffix intent whose only claimant is `marker:"intent"` still routes to the pre-pass.)
- A routed test intent with no test-marker body fails with `test_intent_no_test_marker` (specific, recoverable), never a silent skip or a generic verdict.
- The gate rejects `@intent`/`@intent-file` claiming a test-suffix intent (`non_test_marker_on_test_intent`) with a fix-it message; it does **not** reject `@intent-support`, nor `@intent` claiming a non-test intent inside a test file.
- The Engineer instruction + a skill name the test markers; the per-bead task signals a test bead; an end-to-end build of a test-pyramid intent produces a `@intent-test-file`-decorated test that the pre-pass judges (and can reject for genuine test-quality reasons — the §3.4 guarantee is back in force).
- One source of truth: a single shared suffix predicate is consumed by the CLI verifier, the orchestrator, and inspect; no divergent per-consumer copy remains.
