## Context

This change resolves RFC App. **D.33** — a model-call error-handling gap surfaced by the Phase-6 greenfield POC, orthogonal to the D.29–D.32 verification-channel series. It is the **D.26 lesson generalized from the Engineer path to the model-call path**: *a deterministic, content/limit-shaped failure must not be cold-retried as transient plumbing, and must not be fatal.*

The board (architect, backend, AI eng, Fowler) independently verified the failure chain against live code and converged in one round. The verified facts the design rests on:

- **The spawn + cap.** `claudeCodeModelClient` (`runtime/verifier/src/modelClient.ts:130-159`) spawns `claude --print --output-format json --model <m> --max-turns 3 --disallowed-tools …DISABLED_TOOLS` (`:138-144`). `DISABLED_TOOLS` (`:90`) is a **9-name denylist**. `runClaude` (`:92-121`) rejects a non-zero exit with `new Error("claude CLI exited <code>: <stderr.slice(0,500)> <stdout.slice(0,500)>")` (`:112`); the stdout holds the CLI's result envelope `{"type":"result","subtype":"error_max_turns","stop_reason":"tool_use","num_turns":4,…}`.
- **The misclassification.** `isTransportError` (`test-harness/src/transportError.ts:24-30`) returns true on errno codes, on `error.name==="SyntaxError"`, and on `/claude CLI (timed out|exited)/.test(message)` — so it matches `error_max_turns`. The file's own doc (`:1-18`) scopes "transport" to **plumbing only** (timeout / non-zero exit / spawn errno / malformed envelope) and says programming errors "must propagate and fail the suite loudly, never be bookkept as model noise."
- **The cold-retry-to-throw.** `withTransportRetry` (`runtime/benchmark/src/transportRetry.ts:24-35`): rethrows a non-transport error immediately (`:28/:32`); retries a transport error once; throws `TransportLegFailure` (`:33`) on a second transport death.
- **The wrap + the uncaught paths.** `cli/src/implement.ts:326-329` — `modelClient.complete = (req) => withTransportRetry(() => rawModelClient.complete(req))`. The `taskRunner` ELSE branch (`:377`) and both verifier callers — `verifyIntent` (`runtime/verifier/src/procedure.ts:108`) and the test pre-pass (`runtime/benchmark/src/testPrepass.ts:79`) — `await modelClient.complete` with **no try/catch**; they only convert an unparseable *response* into a **returned** `verifier_model_call_failed` (`procedure.ts:116-117`, `testPrepass.ts:81-82`), never a *throw*.
- **The seam.** `spawnSubAgent` (`runtime/orchestrator/src/spawn.ts:98-216`) returns `RuntimeResult<SpawnOutcome>`; pre-spawn failures are already **returned** errors (`:106,109,114`). It awaits `verifierFactory` (`:146`) and `taskRunner` (`:165`) with **no try/catch**.
- **The short cycle.** `runtime/short-cycle/src/loop.ts` propagates a **returned** `{success:false}` spawn (`:148,169`) and converts a `duskError` verdict to a returned `verifier_model_call_failed` (`:171-172`). It does **not** catch a thrown error from `deps.spawn`.
- **The crash stack** pins the crashing caller to `taskRunner` (the reasoning sub-agent ELSE branch) via `spawnSubAgent → runShortCycle → processBead → runImplement → exit 1`. All three caller paths (reasoning, verifier, pre-pass) crash identically on a thrown model-call failure; `runImplement`'s `try…finally` (`runtime/orchestrator/src/stateMachine.ts`) has no `catch`.
- **Facet A facts.** `DISABLED_TOOLS` is incomplete vs the CLI's real built-in set (missing `TodoWrite`, `NotebookEdit`, `BashOutput`, `KillShell`, `SlashCommand`, `ExitPlanMode`, plus any MCP tools — a non-listed tool is a genuine, non-denied `tool_use`). The `claude` CLI (v2.1.153) supports `--tools ""` = "disable all tools" (verified via `claude --help`) — a zero-tool allowlist.
- **Dependency direction.** `@dusk/test-harness` (home of `isTransportError`) depends only on `@dusk/core-schema`; `@dusk/runtime-verifier` (home of `modelClient.ts`) depends on `@dusk/test-harness` (dev). A typed-error *class* in `modelClient.ts` imported by `transportError.ts` would invert that edge → import cycle. (Both depend on `core-schema`, the escape hatch if a type is ever needed.)
- **Error kinds.** `verifier_model_call_failed` and `task_tool_call_failed` already exist in `DUSK_ERROR_KINDS` (`core/schema/src/duskError.ts:31,41`) — no schema change needed.

## Goals / Non-Goals

**Goals:**
- A deterministic, content/limit-shaped model-call failure is classified **non-transport** (not cold-retried).
- Such a failure is **surfaced as a returned failure** the short cycle + recovery ladder handle — never an uncaught fatal crash.
- The surfacing is **honest**: a genuine programming bug still propagates loud; nothing is swallowed into a false pass.
- Reduce the *rate* at which the limit is hit via tool-surface removal — as defense-in-depth, not a correctness claim.

**Non-Goals:**
- Reshaping the verification logic (orthogonal to D.29–D.32).
- Removing `--max-turns` (kept as a blast-radius backstop; D.26's carve-out stands).
- Porting D.26's salvage-and-continue (a model call has no partial artifact — `stop_reason:"tool_use"` → no verdict).
- A new `DuskError` kind (the existing two fit).
- Resting any correctness guarantee on model behavior (`--tools ""` is a rate-improver only).

## Decisions

### D1 — Classify at the source by the result-envelope, structurally (Facet B.i)
The principled boundary: **transport = no model-level result envelope was produced** (timeout, spawn errno, malformed/absent JSON — the plumbing failed); **non-transport = the CLI returned a well-formed result envelope carrying an error subtype** (`error_max_turns` and siblings — the plumbing *succeeded*; the model ran). `runClaude` is the one frame that holds the structured envelope before it is collapsed into an `Error.message`; on a non-zero exit it SHALL attempt `JSON.parse(out)` and, if the parse yields `{type:"result", subtype:"error_*"}` (an error/limit subtype), throw an error **tagged** with that subtype (e.g. `Object.assign(new Error(msg), { duskModelExit: subtype })`). `isTransportError` SHALL add one guard at the top: a tagged error is **not** transport. *Alternative considered & rejected:* extend `TRANSPORT_MESSAGE_RE` with a negative match on `error_max_turns` — rejected: it re-derives, lossily (the message is 500-char-truncated), a fact that was structured one frame earlier, perpetuates the stringly-typed seam, and invites an endless `error_max_turns|usage_limit|…` alternation. *A typed-error class* was also considered and rejected for this change: it would invert the `runtime-verifier → test-harness` dependency edge (cycle); the structural tag needs no cross-package import and no new exported symbol.

### D2 — Surface, don't crash, at the spawn seam (Facet B.ii — the correctness center of gravity)
`spawnSubAgent` is the **one-source-of-truth seam**: all model-call caller paths funnel through it (reasoning via `taskRunner`, verifier + pre-pass via `verifierFactory`), and it already models failure as a **returned** `RuntimeResult`. It SHALL wrap the `verifierFactory` await (`spawn.ts:146`) and the `taskRunner` await (`:165`) in a try/catch that, on a **classified model-call/CLI failure**, returns the surfaced failure:
- **verifier/pre-pass path** → set `verdict` to a `duskError("verifier_model_call_failed", …)`; this flows through `value.verdict` and the existing `loop.ts:171` `isDuskError(verdict)` handling produces the returned `verifier_model_call_failed` the recovery ladder routes. (NB: `loop.ts:172` re-wraps any non-verdict into its own `verifier_model_call_failed` with `recoverable:false` + a generic message — pre-existing behavior; so the *kind* the ladder routes survives, but the surfaced verdict's `recoverable`/detail does not persist on this path. This is acceptable — the failure is legible and routed; we do not over-claim `recoverable:true` on the verifier branch.) The pre-pass rides the **same** `verifierFactory` await (`implement.ts:395-397` calls `realTestPrepassVerdict` *inside* `verifierFactory`), so there is no separate pre-pass seam to wrap.
- **reasoning/`taskRunner` path** → `return { success:false, error: duskError("task_tool_call_failed", …, { recoverable: true }) }`; the short cycle propagates a returned `{success:false}` and `runImplement` surfaces it as the legible `implement: <kind> — <message>` outcome (`cli/src/implement.ts`), no stack trace.

**The discarded-result call site (`loop.ts:201`) MUST also be fixed** — re-audit finding. The short-cycle **bead-orchestrator tick** (`loop.ts:201-214`) is a `taskRunner` ELSE-branch spawn (`role:"bead-orchestrator"` → `subagentType ≠ dusk-engineer` → `modelClient.complete`) — it is the path the crash stack actually pinned — and its `RuntimeResult` is **discarded** (no `if (!success)` check). Converting its throw to a returned `{success:false}` at the seam would otherwise be **silently ignored** at `:201` (a new silent false-success — exactly the D3 violation, relocated to the call site). The engineer (`:139,148`) and verifier (`:160,169`) spawns already check `.success`; the bead-orchestrator tick SHALL be made to check it too (`const tick = await deps.spawn(...); if (!tick.success) return tick;`) so its model-call failure is surfaced, not dropped.

*Alternative considered & rejected:* catch in each caller — rejected (triplicated logic in three packages; the next model-call caller added later would be silently unprotected — the "two places decide the same thing" trap the D.30/D.32 boards kept paying down). *Also rejected:* add a `catch` to `runImplement`'s `try…finally` — it sits *above* the per-bead freeze/livelock loop, so it would discard the bead-level legible failure the returned-error path preserves. The seam is the right altitude.

### D3 — The catch is NARROW (the honesty bar — Fowler's binding constraint)
The seam catch SHALL convert **only** a classified model-call/CLI failure, decided by a shared predicate `isModelCallFailure(err)` := `isTransportError(err)` (genuine transport — but note `withTransportRetry` retries those before they reach the seam, and a *two-death* `TransportLegFailure` does NOT itself match `TRANSPORT_MESSAGE_RE`, so it is caught by the next arm) **or** `err?.name === "TransportLegFailure"` **or** `typeof err?.duskModelExit === "string"` (the limit-shaped tag from D1). **`isModelCallFailure` MUST detect `TransportLegFailure` STRUCTURALLY by `name`, NOT via `instanceof`** — re-audit finding: `TransportLegFailure` is exported from `@dusk/runtime-benchmark`, which `@dusk/core-schema` must not depend on; an `instanceof` reference would force a new package edge and recreate exactly the dependency cycle D1's structural tag was chosen to avoid. A `name`/field check needs no import. **Placement:** the classifiers (`isTransportError` + `isModelCallFailure`) live in the `@dusk/core-schema` LEAF (re-exported from `@dusk/test-harness` for back-compat) — because `@dusk/test-harness` is a **dev-only** dependency of `@dusk/runtime-orchestrator`, so `spawnSubAgent` (production code) cannot import the predicate from `test-harness`; `core-schema` is the runtime leaf everyone shares. This realizes the Lead Architect's "one source of truth for failure classification". **Every other throw — `TypeError`, `RangeError`, assertion failures, a returned `internal_error`, anything unclassified — MUST be re-thrown** and fail loud, mirroring `isTransportError`'s existing rule verbatim. A bare `try/catch → verifier_model_call_failed` would swallow a genuine programming bug into a benign "model call failed" — a **silent false-recovery**, which by this project's honesty bar is *worse* than the loud crash it replaces. This is the single most important correctness property of the change after D2.

### D4 — Both B.i and B.ii are required; neither alone fixes the crash
Narrowing the classifier alone (D1 without D2): once `error_max_turns` is non-transport, `withTransportRetry` rethrows the raw error immediately (`transportRetry.ts:28`) and it is *still* uncaught through `taskRunner`/`spawn` → still exit 1. The seam catch alone (D2 without D1): non-fatal, but `withTransportRetry` still cold-retries a deterministic failure once (wasted call) and the failure is dishonestly booked as a transport blip. They are complementary: D1 makes the classification honest (no pointless retry), D2 makes the failure non-fatal + surfaced. Ship both.

### D5 — Remove the tool surface; keep the cap as a backstop (Facet A — defense-in-depth only)
A denylist (`--disallowed-tools`) registers the tools in the API request — the model sees them, attempts, is denied, re-attempts → turn burn — and is provably incomplete (a non-listed tool is a genuine, completable `tool_use`). Replace it with `--tools ""` (zero-tool allowlist) at `modelClient.ts:143` so `tool_use` is structurally impossible in the common case. This is **defense-in-depth with zero correctness weight**: MCP tools, future CLI tools, and prompt-injected `tool_use` can still occur, so the correctness rests **entirely** on D2/D3. `--max-turns 3` is **kept** as a pure blast-radius backstop — D.33 *refines* D.26's carve-out (the cap is fine as a bound) rather than reversing it; what D.26 omitted is that *hitting* the bound must be non-fatal + surfaced (D2). The `:138-139` comment whose premise ("the model recovers and answers in text") the crash falsified SHALL be rewritten to state the new posture (tools removed at the request surface; the cap is a backstop; hitting it is non-fatal + surfaced). *Fork resolved:* the AI-eng lens proposed lowering the cap to 1–2 for honesty; the backend lens wanted it kept as a backstop. Resolution: **keep `--max-turns 3`** — once hitting it is non-fatal (D2) the cap value carries **no correctness weight**, so there is no reason to re-tune it in this change; keeping the shipped value is the conservative choice and avoids resting a new decision on the CLI's turn-accounting behavior (the observed `num_turns:4`-at-cap-3 is unexplained and out of scope — it is an open CLI-behavior question, not a mechanical fact this change should lean on). The dishonest part is the *comment*, not the number; fix the comment.

## Risks / Trade-offs

- **[Sibling error subtypes]** — a non-`error_max_turns` error subtype (e.g. `error_during_execution`) could reintroduce the crash if classified narrowly by name. **Mitigation:** D1 classifies by "a well-formed result envelope with an error subtype," not a subtype allowlist — any such envelope is non-transport and (via D2) surfaced, not fatal.
- **[Over-broad catch swallows a real bug]** — the gravest failure mode. **Mitigation:** D3 mandates the narrow predicate; the regression suite includes a "`taskRunner` throws a `TypeError` → propagates, not swallowed" test.
- **[`realAuditCall.ts` regression]** — a separate `withTransportRetry` consumer (`runtime/benchmark/src/realAuditCall.ts:72,106`). **Mitigation:** narrowing the transport set only makes a deterministic `error_max_turns` there fail *sooner/louder* (it already treats `verifier_model_call_failed` as a recoverable null with one retry then fails loud) — never silently. No behavior is loosened.
- **[`--tools ""` interaction]** — could it suppress the JSON result envelope or fight `--max-turns`? **Mitigation:** the result envelope is emitted regardless of the turn cap (it is exactly how `error_max_turns` is observed); `--tools ""` only changes the *request* tool set. Verified the flag spelling against `claude --help`.
- **[Pile-on]** — Fowler's anti-pile-on. **Mitigation:** **two** mechanism pieces (D1 classify-at-source, D2 surface-at-seam) that are *both* load-bearing (D4), **one** honesty constraint (D3), and **one** zero-weight rate-improver (D5). No third mechanism; salvage-and-continue explicitly declined (no artifact).

## Migration Plan

Additive + corrective within the dusk monorepo; no data migration. Sequence: (1) tag the `runClaude` throw on an error-subtype envelope (D1) + the `isTransportError` guard; (2) the narrow `isModelCallFailure` predicate + the `spawnSubAgent` catch-and-return (D2/D3); (3) `--tools ""` + comment rewrite (D5); (4) regression tests (the §8 reproductions) + integration. `withTransportRetry`'s genuine-transport behavior is unchanged. This is a v1.x corrective to shipped v1 behavior, surfaced by the POC; it lands **before the Phase-6 POC resumes** (the build is paused at the bootstrap-tree layer pending it).
