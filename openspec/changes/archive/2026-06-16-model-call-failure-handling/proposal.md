## Why

A Phase-6 POC build crashed: `dusk implement` died with an **uncaught `TransportLegFailure` → exit 1**, pre-merge (no bead reached main). The mechanism, verified end-to-end against live code (RFC App. D.33):

A no-tools JSON model call — `claudeCodeModelClient` spawning `claude --print --output-format json --max-turns 3 --disallowed-tools …` (`runtime/verifier/src/modelClient.ts:138-144`), used by the Verifier, the Stage-1 test-body pre-pass, and the non-Engineer reasoning sub-agents — burned its turn budget **attempting tools** (`stop_reason:"tool_use"`, `num_turns:4`) and exited `error_max_turns` (non-zero). `runClaude` rejected with `"claude CLI exited 1: …"` (`modelClient.ts:107-113`). `isTransportError` matched `TRANSPORT_MESSAGE_RE = /claude CLI (timed out|exited)/` (`test-harness/src/transportError.ts:22,29`) → classified it **transport**. `withTransportRetry` (`runtime/benchmark/src/transportRetry.ts:24-35`) cold-retried the **identical deterministic** call (it reproduced `error_max_turns` exactly — both `num_turns:4`), and the second "transport death" threw `TransportLegFailure`. That throw is **uncaught on every model-call caller path**: the `taskRunner` ELSE branch (`cli/src/implement.ts:377`), `verifyIntent` (`runtime/verifier/src/procedure.ts:108`), and the test pre-pass (`runtime/benchmark/src/testPrepass.ts:79`) all `await modelClient.complete` with no try/catch; the spawn seam `spawnSubAgent` awaits `taskRunner`/`verifierFactory` with no try/catch (`runtime/orchestrator/src/spawn.ts:146,165`); and the short cycle handles only **returned** `{success:false}` failures (`runtime/short-cycle/src/loop.ts:148,171`), never a throw. So it propagated to `runImplement` (whose `try…finally` has no `catch`) → exit 1.

This is the **D.26 lesson un-applied to the model-call path.** D.26 fixed the analogous case on the **Engineer** path (a deterministic wall-clock timeout was transport-misclassified → cold-retried → fatal, discarding a correct partial worktree) via salvage-and-continue. The model-client `error_max_turns` path runs through the *same* `withTransportRetry` + `isTransportError` and inherited none of the lesson. A deterministic, content/limit-shaped failure is still being **cold-retried as transient plumbing** and is **fatal + uncaught** — violating the project's "no silent behavior, no fatal crash on a deterministic failure" bar.

This change resolves the gap from first principles, ratified by a four-lens arch board (architect, backend, AI eng, Fowler) over an investigate→debate→converge cycle (unanimous APPROVE-WITH-CHANGES; see design "Review round"). Grounded in RFC App. **D.33** (generalizing **D.26**'s transport-classification lesson to the model-call path), the transport-failure amendment (Phase-4 board S7), and §6.4.1 (the recovery ladder).

## What Changes

- **Honest classification at the source (the root fix — Facet B.i).** `runClaude`, on a non-zero CLI exit whose stdout parses to a result envelope carrying an **error subtype** (`error_max_turns` and siblings — the plumbing succeeded; the model ran and produced a well-formed envelope), SHALL tag the thrown error structurally (a `duskModelExit` discriminant naming the subtype). `isTransportError` SHALL return `false` for a so-tagged error. A deterministic limit failure is therefore **never cold-retried** (retrying an identical deterministic call is waste, and the second death is what manufactured the fatal `TransportLegFailure`). Classification lives at the throw site where the **structured** `subtype` is in hand — NOT as a new alternation in the stringly-typed `TRANSPORT_MESSAGE_RE` regex over a 500-char-truncated message. The structural tag also avoids the `runtime-verifier → test-harness` dependency cycle a typed-error *import* would create (`test-harness` depends only on `core-schema`; `runtime-verifier` depends on `test-harness`).
- **Surface, don't crash, at the spawn seam (the correctness fix — Facet B.ii).** `spawnSubAgent` SHALL wrap the `verifierFactory` and `taskRunner` awaits in a **narrow** try/catch that converts **only a classified model-call/CLI failure** (transport- or limit-shaped) into a **returned** failure: a `verifier_model_call_failed` (recoverable) verdict for the verifier path, and a `task_tool_call_failed` (recoverable) `RuntimeResult` for the reasoning/`taskRunner` path. These are the existing signals the short cycle + recovery ladder already route — the failure flows to a legible `implement: <kind> — <message>` outcome instead of an exit-1 stack trace. **The catch is narrow by mandate:** programming errors (`TypeError`, assertion failures, `internal_error`, any non-classified throw) MUST propagate and fail loud — mirroring `isTransportError`'s own rule ("programming errors are never bookkept as model noise"). A bare catch that relabels every throw would trade a loud crash for a **silent false-recovery** and is rejected.
- **Both parts are load-bearing.** Narrowing the classifier **alone** is a non-fix: once `error_max_turns` is non-transport, `withTransportRetry` rethrows the raw error immediately (`transportRetry.ts:28`) and it is *still* uncaught → still exit 1. The spawn-seam catch **alone** "works" but keeps cold-retrying a deterministic failure once (wasteful + dishonest). Ship both.
- **Remove the tool surface (Facet A — defense-in-depth, a rate-improver, zero correctness weight).** Replace `--disallowed-tools …DISABLED_TOOLS` (a denylist that registers the tools in the request and is provably incomplete vs the CLI's real built-in set) with `--tools ""` (a zero-tool **allowlist** the CLI supports → `tool_use` structurally impossible, modulo MCP/future-tool/prompt-injection edge cases) at `modelClient.ts:143`. `--max-turns 3` is **kept** as a pure blast-radius backstop (D.33 refines, not reverses, D.26's carve-out of the cap: the cap is fine *as a bound*; what was missing is that *hitting* it must be non-fatal + surfaced); the code comment whose premise ("the model recovers and answers in text") was falsified is rewritten.

## Capabilities

### New Capabilities

- `model-call-failure-handling`: A deterministic, content/limit-shaped model-call failure (`error_max_turns` and siblings) is classified **non-transport** (not cold-retried) and **surfaced as a returned failure** the short cycle + recovery ladder handle — never an uncaught fatal crash, never a silent false-recovery. Classification is structural, at the throw site. The spawn-seam catch is narrow (programming errors still propagate loud). Tool suppression via `--tools ""` is a defense-in-depth rate-improver, never a correctness guarantee.

## Impact

- **Code touched (dusk monorepo):** `core/schema/src/modelCallError.ts` (NEW — the single source of truth: `isTransportError` with the `duskModelExit` guard + the `isModelCallFailure` seam predicate, detecting `TransportLegFailure` by `name` not `instanceof` to avoid a package cycle); `test-harness/src/transportError.ts` (now re-exports both from `@dusk/core-schema` for back-compat — `test-harness` is a dev-only dep of the orchestrator, so the runtime seam must source the predicate from the `core-schema` leaf); `runtime/verifier/src/modelClient.ts` (tag the `runClaude` throw on an error-subtype envelope via `modelExitSubtype` at `:107-130`; `--tools ""` + rewritten comment at the spawn args); `runtime/orchestrator/src/spawn.ts` (narrow try/catch around the `verifierFactory` await `:146` and the `taskRunner` await `:165`, returning the surfaced failure); `runtime/short-cycle/src/loop.ts` (check the bead-orchestrator tick's result at `:201` — currently discarded — so a surfaced failure there is propagated, not silently dropped).
- **Bound, not reshaped:** `withTransportRetry`'s genuine-transport retry (CLI timeout / spawn errno / malformed envelope still retried once) is **unchanged** — only what counts as transport is narrowed. The short cycle, recovery ladder, verifier procedure, and the no-leak invariant are untouched. `runtime/benchmark/src/realAuditCall.ts` (a separate `withTransportRetry` consumer) is not regressed (a narrower transport set only makes it fail *louder/sooner* on a deterministic error, never silently).
- **Determinism posture:** the classification guard, the narrow spawn-seam catch, and the return-vs-throw are **zero-model mechanical** — the correctness guarantees, tested deterministically (incl. the §8 reproductions as regression tests). `--tools ""` is the single model-facing piece — it lowers the *rate* at which the limit is hit but is never relied on for correctness (the mechanical guards make a deterministic model-call failure non-fatal regardless of model behavior).
- **Reconciliation with D.26:** D.26 endorsed the Verifier's `--max-turns 3` and rejected a cap on the Engineer; D.33 keeps the cap as a bound and adds the missing clause — *hitting* the bound is non-fatal and surfaced. Salvage-and-continue (D.26's mechanism) does **not** transfer: a model call has no partial artifact (`stop_reason:"tool_use"` → no verdict), so the analog is "surface a returned failure into the recovery ladder," not "salvage a draft."
- **Non-goals:** NOT reshaping the verification logic (orthogonal to D.29–D.32). NOT removing `--max-turns` (kept as a backstop). NOT a salvage-and-continue port (no artifact to salvage). NOT a new `DuskError` kind (the existing `verifier_model_call_failed` + `task_tool_call_failed` fit). NOT touching the POC repo or the Phase-6 change.

## Verifiability / acceptance

Success = a deterministic/content-limit model-call failure is **never silently accepted and never an uncaught fatal crash** — it is classified honestly and surfaced/handled:
- `isTransportError(new Error('claude CLI exited 1: {"type":"result","subtype":"error_max_turns",…}'))` — once the throw is tagged at the source — is **`false`** (zero-model unit). A genuine transport error (`"claude CLI timed out"`, an `ENOENT`, a `SyntaxError` envelope) is still **`true`**.
- `withTransportRetry(observe)` where `observe` rejects twice with a tagged `error_max_turns` error does **NOT** throw `TransportLegFailure` — it rethrows the (single, non-retried) classified error, which the spawn seam then catches (zero-model unit).
- A `spawnSubAgent` whose injected `taskRunner` / `verifierFactory` throws a classified model-call failure returns a **`{success:false}`** with `task_tool_call_failed` / a `verifier_model_call_failed` verdict — never propagates the throw (zero-model unit). A `taskRunner` that throws a `TypeError` (a programming bug) **still propagates** — the catch does not swallow it.
- End-to-end (zero-model where possible): a short-cycle spawn whose model call deterministically fails surfaces a legible returned failure that re-enters the recovery ladder; the run does not exit 1 with a stack trace.
- `--tools ""` is present in the model-client spawn args; the falsified comment is corrected; `--max-turns 3` remains.
