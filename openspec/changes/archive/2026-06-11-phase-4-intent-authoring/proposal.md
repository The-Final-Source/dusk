## Why

Phase 3 shipped `dusk_implement` end-to-end and produces atomic commits on `main` — but two of its surfaces still bottom out in stubs: when the Decomposer hits an unresolved intent it writes an `ImplementCheckpoint` and returns `implement_paused_for_authoring`, but no real `dusk_author_*` flow exists for the harness to drive; when a Test-Verifier livelock is resolved via `dusk_resolve_livelock({verb: "modify_triple"})` the implementation accepts an inline `payload` carrying the rewritten triple (a deliberate placeholder per design Q4) because no dialog continuation pattern existed yet. Without Phase 4 these stubs cannot be lifted: there's no way for an operator to author a complete schema-valid intent set through a multi-turn dialog, no way to drive Recovery-Ladder L2's `intent-proposal.yaml` artifact into an actual intent revision, and no way to close the `dusk_implement` ↔ `dusk_author` loop end-to-end. Phase 4 is also the only place where Phase 3's frozen `ImplementCheckpoint` JSON shape gets a real consumer — proving the cross-proposal interface decision was correct (or surfacing where it wasn't).

This change delivers **exactly Phase 4 of the v9 implementation plan** (`docs/rfcs/001-mvp-rfc/v9-implementation-plan.md` lines 598–705), grounded in RFC §5, §3.1, §3.1.1, §3.2.1, §3.4.1, §6.4.1, §9.6 (`dialog` scope), §10.1, §10.1.1, App. A.11, App. D.10, App. D.19.

## What Changes

- **`packages/runtime/author`** — Author role (`memory: dialog`) runtime implementing the **5-stage continuation flow** per RFC §5: Stage 1 Intake & Framing → Stage 2 Discovery & Tension Detection (via **agent-driven grep over `.ia/intents/`**, no vector search) → Stage 3 Industry-Practice Injection (from training + skill, **no runtime canonical-library lookup**) → Stage 4 hierarchical Drafting (with test-pyramid child proposal) → Stage 5 Commit. Each user decision SHALL be a real branching point exposed as the next `next_question`.
- **Stage 4.5 validations** — a synchronous pre-commit pass running the Phase-1 parser's matrix-predicate negation detection + closed-vocabulary antecedent grammar + typed `relates_to` checks against every drafted triple. Violations bounce the Author back to Stage 4 with a hint naming the relevant skill (`polarity-decision`, `implies-antecedent-grammar`, `typed-relates-to`). No intent ever commits without passing 4.5.
- **Author skills** — `polarity-decision`, `typed-relates-to`, `implies-antecedent-grammar`, `tension-detection`, `discovery-grep-patterns`, `best-practices-application`, `test-pyramid-proposal` (the tier-1/2 baseline shipped in Phase 2 is filled in here with the real authoring guidance — Phase 2 shipped the skill files; Phase 4 fills them).
- **Dialog directory lifecycle** — `.ia/runtime/dialogs/<dialog-id>/` created by `dusk_author_start`, destroyed by `dusk_author_finalize`, GC'd via the existing Phase-3 `dusk doctor --gc-dialogs` after 24h. `dialog_id` format `dlg_<14-digit-yyyymmddhhmmss><3-digit-seq>` per App. D.8.
- **`DialogState` shape (NEW frozen seam in `@dusk/core-schema`)** — `{schema_version: 1, dialog_id, request, current_stage: 1 | 2 | 3 | 4 | "4.5" | 5, transcript: [{role, content, stage, at}], intents_drafted: Intent[], created_at, last_touched_at}`. Phase 5's audit reads the transcript as the human-negotiation record.
- **Continuation MCP tools** — `dusk_author_start({request})` → `{dialog_id, stage, next_question}`; `dusk_author_continue({dialog_id, response, payload?})` → `{stage, next_question}` OR `{finalize_ready: true}`; `dusk_author_finalize({dialog_id})` → `{intents_created[]}`. Uniform `DuskError` envelope with the three Phase-2-pinned author kinds (`author_dialog_id_unknown`, `author_stage_invalid_response`, `author_intent_schema_invalid`) — Phase 4 emits them for real. `/dusk-author` slash command wrapper.
- **Decomposer-Author bridge** — Phase 3's `bead-decomposition` unresolved-intent escalation path is **wired** to the real Author flow: the Decomposer still writes the same `ImplementCheckpoint` (shape unchanged per Phase 3 D4) but **`suggested_dialog_seed` content is enriched** from the naive `unresolved_refs.join(", ")` to a Stage-1-framed prompt seeded with the unresolved-ref's surrounding intent context (descendants, siblings, related-to edges). The shape stays frozen; only content evolves.
- **Recovery Ladder L2 recovery action** — Phase 3's `recovery-ladder` ships L2's *artifact* (`intent-proposal.yaml`) + *error contract* (`bead_intent_revision_needed`, `recoverable: true`); Phase 4 ships L2's *recovery action*: the user invokes `dusk_author_continue` against the proposal, the Author runs Stage 4 + 4.5 over the proposed rephrasings, finalize writes the refined intent into `.ia/intents/<path>/intent.yaml`, and the user re-invokes `dusk_implement` to retry the bead.
- **Livelock `modify_triple` rewire** — Phase 3's `livelock-detection` ships `modify_triple` as an inline-payload form (the user passes `{edited_triple}` directly). Phase 4 **rewires** the verb to open a scoped single-stage `dusk_author_continue` dialog keyed to the failing triple from `TestVerifierLivelockReport`; finalize writes the edited triple back into the intent file in-place; bead resumes at the previously-failing iteration with the refreshed intent visible to the next Verifier spawn.
- **`dusk://dialogs/active` + `dusk_list_dialogs`** — paired MCP resource + tool returning outstanding-dialog summaries (mirroring Phase 3's `dusk://implement-checkpoints` pattern). Each entry: `{dialog_id, request, current_stage, created_at, last_touched_at}`.

## Capabilities

### New Capabilities

- `dialog-state`: `DialogState` shape in `@dusk/core-schema` (the frozen cross-proposal interface Phase 5 audit consumes) + `.ia/runtime/dialogs/<dialog-id>/` directory lifecycle + `dialog_id` format + 24h GC integration.
- `author-five-stage-flow`: The Author role runtime — 5-stage continuation flow (intake → discovery via grep → practice injection from training → drafting → commit) + Stage 4.5 pre-commit validations + the 7 tier-1/2 author skills filled in.
- `author-mcp-surface`: `dusk_author_start` / `dusk_author_continue` / `dusk_author_finalize` MCP tools + `/dusk-author` slash command wrapper + uniform `DuskError` envelope.

### Modified Capabilities

- `bead-decomposition`: `suggested_dialog_seed` content evolves from the naive `unresolved_refs.join(", ")` to a Stage-1-framed prompt seeded with surrounding intent context. **`ImplementCheckpoint` shape unchanged** per Phase 3 D4.
- `recovery-ladder`: L2's *recovery action* (`dusk_author_continue` consuming `intent-proposal.yaml`) is now operative — Phase 3 shipped the artifact + recoverable error; Phase 4 ships the wire that takes the user from the error to a finalized refined intent.
- `livelock-detection`: `dusk_resolve_livelock({verb: "modify_triple"})` rewires from the Phase-3 inline-payload form to a scoped `dusk_author_continue` dialog; the `TestVerifierLivelockReport.failing_triple` from Phase 3's frozen shape is the dialog seed.
- `dusk-cli-substrate`: Adds `dusk author <request>` (direct-invocation CLI mirror of `dusk_author_*` for debugging); `dusk doctor --gc-dialogs` continues operable (already shipped in Phase 3) but now reaps real dialog state.
- `mcp-read-surface`: Adds `dusk://dialogs/active` + `dusk_list_dialogs` populating with real outstanding dialogs.

## Impact

- **New packages:** `packages/runtime/author` (the Author runtime + 5-stage state machine + Stage 4.5 validations + author skill content).
- **Bound to Phase-1+2+3 seams (no changes):** schema types, decoration record, derived-index query interface (snapshot read), `Rejection`/hook contract, `dusk.config.yml` shape, test harness; `SubAgentTrace` + `Verdict` + `VerifierFactory` + `spawnSubAgent` + bead memory + `compact()` + `ModelClient` + `DuskError` + `dusk_inspect` shape; `ImplementCheckpoint` (shape unchanged; content enriched) + `TestVerifierLivelockReport` + the resolve-livelock 3-verb contract.
- **App-package surface (api/web/shared/hooks/mobile):** untouched (Phase-5 dogfood targets).
- **External dependency:** the Author runtime uses the ambient Claude Code CLI `ModelClient` for the LLM half of Stages 1–4 — same path Phase 2's Verifier uses. No new auth surface.
- **Determinism posture:** the 5-stage state machine + Stage 4.5 validations + dialog lifecycle + cross-tool resume (P4-T8) run **control-flow** tests against deterministic injected responses (a Stage-script driver replacing the user; analog of Phase 2's scripted-verdict double for the Author surface). LLM-content tests (P4-T2 tension classification, P4-T4 polarity emission, P4-T5 antecedent emission, the Stage-3 greenfield path) run against the **real frontier model** at `temperature: 0` with the pre-registered `N=3, threshold ≥2/3` protocol.
- **Non-goals:** Phase 5 (fresh-Verifier audit, `/dusk-doctor --static-analysis`, observability sinks, benchmark harness, seeded-violations fixture, dogfooding on real packages). Any embedding/vector/RAG substrate (RFC §8.10 explicitly defers — Stage 2 is grep-only in v1). Any runtime canonical-library lookup (RFC §8.11 — Stage 3 is training+skill only). Reshaping any Phase 1/2/3 capability shape.

## Verifiability / acceptance

Success = **every behavioral test P4-T1..P4-T13 passes** against real dependencies per the plan — real file system, real ambient-model invocations for LLM-content legs, real `dusk_implement` pipeline for the cross-tool resume test. The **phase-landing smoke test** ("author then resume, including a conditional intent") must go green: start `dusk_implement` against an unauthored target → pause → drive the full 5-stage flow including a `polarity: negative` triple AND a `compose: implies` intent → finalize → resume the paused pipeline → completes with a commit; then age a second abandoned dialog past 24h and prove `dusk doctor --gc-dialogs` reaps it. The **cohesive-landing checklist** (plan lines 698–705) is the archival gate, including: the Decomposer escalation point now invokes the real Author flow (no Sprint-5 stub remaining); Stage 4.5 validations all bounce real violations; authored intents are schema-valid v2 and immediately resolvable; no code is modified during authoring.
